Core architecture rule

Authenticate the user before sensitive processing. Authorize every protected action at the gateway and enforce resource permissions again in backend APIs.

The LLM may decide which tool to request; it must never decide whether the user is authorized.

01 · Architecture flow

Correct enterprise AI governance flow

Identity is established first. Retrieval and tool calls follow separate controlled paths, then the response is validated before delivery.

1. Identity & AuthenticationValidate token/session · verify identity · create trusted identity context · reject unauthenticated requests
↓
2. Request Policy & Input ScreeningValidate input · detect abuse/prompt injection · request-level authorization · rate limits
↓
3. AI Agent — C# / Semantic KernelInterpret intent · plan within limits · select from permitted tools · do not trust user-supplied identity claims
↓
4A. RAG Pipeline

Document access control · metadata/tenant filtering · grounded retrieval · source references

4B. MCP Gateway

Authenticate caller/context · authorize tool · validate arguments · rate-limit · audit

↓
5. Backend APIs & DataResource-level authorization · business rules · minimum necessary data · read/write permissions
↓
6. Response ValidationVerify against actual tool/RAG results · sensitive-data checks · safety/policy validation · escalate if uncertain
↓
Final AI ResponseAnswer + evidence/citations where applicable
Important: the RAG branch may return evidence without invoking MCP. Any protected document must be access-checked before it is supplied to the model.

02 · Layer-by-layer controls

Where to apply what — and why

LayerControlsPurpose / example
1. IdentityOIDC/OAuth token validation, session checks, trusted claimsKnow who is asking. Reject invalid or expired credentials.
2. Input / policySchema and size checks, abuse screening, prompt-injection detection, request limitsReject malformed or abusive input early; screening is not a substitute for authorization.
3. AI agentTrusted instructions, bounded planning, tool allowlists, max steps/timeoutsKeep the agent's behavior and autonomy within defined limits.
4A. RAGDocument ACLs, tenant/metadata filters, source IDs, groundingRetrieve only documents the current user may see; cite real sources.
4B. MCP gatewayCaller authentication, tool authorization, argument validation, quotas, audit IDsStop unauthorized tool calls even if the model requests them.
5. Backend APIsResource ownership, business rules, field minimization, transaction checksProtect the actual data/action; never rely only on gateway checks.
6. ResponseGrounding checks, data leakage checks, safety validation, escalationReduce unsupported answers and accidental disclosure before showing output.
7. OperationsAudit logs, metrics, incident response, human review, kill switchDetect failures and misuse; investigate incidents and stop unsafe workflows.
03 · Five principles

Governance is cross-cutting

These principles are not five separate boxes at the end of the pipeline. They influence the design, testing, execution, and monitoring of multiple layers.

⚖️

Fairness

Use consistent, relevant criteria; test outcomes across groups; review high-impact decisions.

🔎

Explainability

Retain evidence, source citations, decision factors, tool outcomes, and policy references.

🔐

Privacy & Security

Minimize data, enforce access controls, protect secrets, and secure logs and transport.

🛡️

Safety

Prevent harmful output and unsafe tool use; test jailbreaks and validate responses.

🎛️

Controllability

Bound execution, require approval, support stop switches, and audit actions.

Practical distinction: prompts guide the model; application policy, gateway checks, backend authorization, and operational controls enforce governance.
04 · Worked example

Query: “Show me EMP202's salary slip”

Assume the signed-in user is EMP101 and has ordinary employee permissions.

1

Authenticate at entry

Validate the token and derive the trusted identity EMP101 from verified claims—not from the prompt.

2

Agent selects a tool

The agent may request get_my_salary_slip, but this request is not authorization.

3

Gateway checks permission

Confirm the caller can invoke the tool and that arguments match the permitted operation. Do not trust an employee ID supplied only by the model.

4

Backend enforces resource access

Payroll checks whether the authenticated identity can access that exact record. If not, deny the request.

5

Safe response and audit

Return a minimal denial message, avoid leaking whether another employee's record exists, and log the security outcome.

Expected outcome: no salary data is returned. The LLM cannot override the gateway or payroll API.
05 · MCP gateway

Security checks for every tool call

🪪

Authenticate the caller

Validate the calling service/user identity using the configured trust model. Propagate user identity securely when delegated access is required.

🔑

Authorize the tool

Apply role and permission policy to the specific tool. Tool discovery or visibility alone is not authorization.

🧾

Validate arguments

Check schema, allowed values, date ranges, resource ownership, and business constraints.

🚦

Limit and monitor

Enforce quotas, timeouts, correlation IDs, structured audit events, and alerts for suspicious patterns.

Do not assume the MCP protocol itself automatically provides your application's complete authentication, authorization, or business policy. Configure and enforce these controls in the actual deployment.
06 · Safety and human oversight

Control actions by risk

Lower risk

Read approved knowledge

Search IT documentation or explain a policy. Still enforce document access, grounding, and output checks.

Read-onlyCitations
Moderate risk

Create a support ticket

Validate fields, confirm the destination, prevent duplicate submissions, and audit the result.

ValidationConfirmation
Higher risk

Change payroll / approve leave

Require explicit permissions, business-rule checks, and an authorized human approval where policy requires it.

ApprovalAudit
Human approval must be bound to the exact action and parameters. Re-check authorization and policy when executing; an approval screen alone is not a security boundary.

Operational kill switch

Provide an administrator-controlled way to disable an agent, a tool, or all write operations during an incident. Log who activated it, when, and why.
